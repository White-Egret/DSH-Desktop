# DSH Desktop

Windows 10/11 轻量桌面端（Tauri v2 + Rust + 原生 HTML/CSS/JS），用于启动、配置、运行、更新本机 npm 全局安装的 DSH（DeepSeek Harness）Web 服务。英文主文档见 [README.md](README.md)。

> **重要 —— 本程序不内置任何运行时**
>
> - 本程序**不内置 Node.js**。
> - 本程序**不内置 DSH**。
> - 也不下载/部署任何便携版 Node/DSH 运行环境。
> - 用户需主动安装 Node.js 与 DSH（首次运行向导可引导安装，见「环境要求」）。

## 概览

- **单窗口设计**：顶部 43.2px 工具栏（操作按钮 + 一行状态：状态点 · 端口 · 版本），DSH 就绪后其 Web 界面**直接内嵌在工具栏下方**，绝不打开默认浏览器（启动命令固定带 `--no-open`）。
- 程序按你配置的路径与端口启动 DSH：先 TCP + HTTP 轮询确认服务真正就绪，再加载页面；若 DSH 在就绪前闪退，立即显示最后一条 stderr 报错，绝不无限等待。
- **只管理自己启动的进程**：退出时用 `taskkill /PID <pid> /T /F` + Windows Job Object 结束本次启动的 DSH 进程树，绝不使用 `taskkill /IM node.exe /F` 这类误杀式命令。

## 功能特性

- 端口可配置（默认 **3080**），路径自动检测 + 首选项页手动选择
- 端口占用保护：提示而非强杀——可连接现有服务、修改端口、重新检测
- 实际地址识别：DSH 输出中打印了真实监听地址时（如 `dsh web: http://127.0.0.1:3080`），优先按该地址加载
- **next 频道的浏览器会话令牌（token）**：DSH `next`（0.1.2+）用每次进程随机生成的启动令牌保护网页——打印的地址形如 `dsh web: http://127.0.0.1:3080?token=...`，裸地址访问会收到 `401 authentication required`。启动器内嵌页面时保留打印的完整地址（含 `?token=...`）；首次带令牌加载后 DSH 会签发签名 cookie（HttpOnly，默认 30 天），刷新与后续启动不再需要令牌。最近一次加载的页面地址也会被记住（config.json 的 `last_url`，每次使用前校验形状与端口），「连接现有服务」与页面重开同样会带上令牌
- 文件日志：Desktop 日志 `%APPDATA%\com.dsh.desktop\desktop.log`；DSH 输出日志 `%USERPROFILE%\.dsh\logs\dsh.log`；UI 提供「打开日志目录」「复制错误信息」「复制日志」
- 刷新页面：只重载内嵌网页，不重启后台服务（`F5` / `Ctrl+R`）
- 一键更新 DSH（npm 全局安装，输出实时可见）：确认弹窗可在 `latest` / `next` 两个频道间任选，升级与退回稳定版同等对待，并提醒先备份 `~/.dsh`
- **安全模式**：用独立纯净家目录（`%USERPROFILE%\.dsh-safe`）在 3081 端口启动 DSH，检查与修复日常环境；只借用 `.credentials.yaml` 一个文件（内容全程不出 Rust 侧），可选「进入时重置基线」把旧安全环境归档而非删除（默认关闭，需要时在首选项开启），退出后自动重启日常实例并验证修复结果 —— 见「安全模式」
- 版本检测同时读取 `latest` 与 `next` 两个 dist-tag（`npm view <包名> dist-tags`），已装版本落后于最新频道时状态栏给出「可更新」标记
- 关闭行为可配：点 X 隐藏到托盘（默认）或退出程序；托盘恢复执行 show + unminimize + set_focus
- 开机自启（官方插件，仅写 HKCU 注册表，无需管理员）；自启时静默托盘化并延迟 12 秒错开冷启动高峰
- 首次运行向导：检测 Node/npm/DSH/pnpm 并引导安装（nodejs.org 官方 LTS 安装包在线下载，或代为执行 `npm install -g @deepseek-ai/dsh`），**可指定 Node / DSH 的安装位置**（如装到 D 盘），全程可跳过；检测到 Node 后还会检查 **pnpm**，缺失时给出一键安装入口，**一键装完 Node 后也会自动执行 `npm install -g pnpm`**（供之后安装 DSH 插件使用）
- **Node.js 最低版本守卫（22.19.0）**：识别「装了但版本过低」的 Node.js，给出带具体版本号的告警，提供一键升级官方 LTS（沿用同一套校验过的安装流程），同时保留「自行到官网下载」与「保留该版本继续」两条路；点「启动」时用大白话说明原因，而不是让 DSH 带着一段看不懂的错误闪退 —— 见「Node.js 版本检查」
- **安装包完整性校验**：调用 `msiexec` 之前，先把下载的 MSI 与该版本官方 `SHASUMS256.txt` 中记录的 SHA-256 逐字节比对；下载落在一次性随机命名的私有临时目录中，用完即删（原先可预测的 `%TEMP%\node-vX.Y.Z-x64.msi` 路径可能被抢先做成符号链接或被替换）。清单取不到、没有该文件条目、或哈希不一致时**直接中止安装，不提供「仍然安装」选项**，请改用手动下载链接
  - **这条校验的信任根在哪里**（安全审查 M-3）：清单与 MSI 走同一条信道，所以完整性校验实际只归约到传输层。为此钉了两件事：下载地址限定为 `https://nodejs.org/dist/`；调用 curl 时带 `--proto '=https' --proto-redir '=https'`，拒绝 https→http 的降级重定向（curl 默认是允许的 —— 代理只要改掉跳转，后续传输连同清单就可能整段走明文，而且哈希照样自洽）。再往下，信任根是 TLS 加**本机的证书库**：Windows 自带的 `curl.exe` 用 Schannel，会信任企业策略或本地恶意程序塞进系统库的根证书，那种环境下攻击者可以同时替换清单与 MSI。这是**环境性局限，启动器自己关不掉它** —— 真正的解法是随程序固定一份期望哈希，目前没有做。
  - PowerShell 回退路径（`curl.exe` 不可用时）改用 `-EncodedCommand` 传 Base64(UTF-16LE) 脚本，URL / 版本号 / 路径都不会被当成 PowerShell 语法解释；临时目录名改由系统 CSPRNG（`BCryptGenRandom`）生成。
- **中英双语界面**：首选项页可切换「语言 / Language」；工具栏、状态区、弹窗、托盘菜单与启动器日志全部跟随切换，并通过 DSH 的 `settings.yaml` 联动 DSH 自身界面语言
- **浅色 / 深色 / 跟随系统外观**：首选项页「外观」三选一；桌面端（工具栏、弹窗、原生标题栏）与内嵌 DSH 页面同步换肤，通过 `settings.yaml` 的 `ui-theme.preference` 联动，**DSH 页面实时跟随、无需重启**
- **窗口布局记忆**：记住主窗口的大小 / 位置 / 最大化状态（官方 `tauri-plugin-window-state`），下次启动原样恢复；显示器拔插后由插件校验坐标，不会出现「窗口飞到屏幕外」—— 见「窗口布局记忆」
- **工具栏显示模式（固定 / 自动隐藏）**：首选项里二选一——常驻，或默认收起在窗口顶部、鼠标移到窗口最上沿 8px 时滑出、离开工具栏半秒后收回（自动模式下内容区占满整窗，工具栏悬浮其上）；`Ctrl+Shift+H` 快速切换。**安全模式强制固定显示** —— 见「工具栏显示模式」
- 单实例锁：重复双击只聚焦已有窗口

## 环境准备（Prerequisites）

启动服务前必须具备：

1. **Node.js（含 npm）**——从官网 <https://nodejs.org/en/download> 安装 LTS 版，**要求 22.19.0 及以上**（见「Node.js 版本检查」一节）；
2. **DSH**——全局安装：

   ```bash
   npm install -g @deepseek-ai/dsh
   ```

3. **pnpm（可选，非必需）**——之后安装 DSH 插件时用它：

   ```bash
   npm install -g pnpm
   ```

   本程序会在首次运行向导里一并检查 pnpm：检测到 Node 而 pnpm 缺失时给出「一键安装 pnpm」入口；选择让程序自动安装 Node 时，装完 Node 会**自动**执行上面这条命令。DSH 本身不依赖 pnpm，跳过不影响启动。

可用以下命令自检：

```bash
node --version
npm --version
dsh --version
```

缺什么时程序会给出明确错误（哪个组件没找到、找过哪些位置、怎么修），不会无限等待。首次运行向导也会自动检测：缺 Node 时提供一键下载运行 nodejs.org 官方 LTS 安装包（运行时在线下载，绝不内置），缺 DSH 时可代为执行 `npm install -g @deepseek-ai/dsh`。**检测到 Node 之后还会检查 pnpm**（之后安装 DSH 插件要用的包管理器）：缺失时向导给出「一键安装 pnpm」入口；而**选择让程序自动安装 Node 的话，装完 Node 会紧接着自动执行 `npm install -g pnpm`**，无需再点一次。pnpm 缺失不阻断任何功能，向导里点「完成」即可跳过。每一步都可以跳过（稍后手动安装），失败原因（无网络/下载失败/权限不足/用户取消）都会明确提示。

### 引导安装 Node.js 的安装位置

「缺少 Node.js」这一步里有一个**安装位置**输入框，**默认已按本机官方默认路径填好**（`%ProgramFiles%\nodejs`，通常就是 `C:\Program Files\nodejs`；Windows 装在 D 盘时它也在 D 盘 —— 这个值由后端按环境变量算，不是前端写死的字符串）。要装到别的盘，把值改成 `D:\nodejs` 之类即可，也可以点「浏览」选文件夹；清空则回到官方默认目录。它最终以 `INSTALLDIR=<路径>` 交给官方 MSI —— 官方安装包的目录页正好绑在这个公开属性上（本机缓存 MSI 的 Property 表实测 `WIXUI_INSTALLDIR = INSTALLDIR`），而程序走的是 `/passive`，那个页面不会被画出来，所以路径只能在这里问。

几条要注意的：

- **用户改过的值不会被覆盖**：安装位置预填的是默认路径，但你一旦手动改过（或「浏览」选过），之后点「重新检测」也不会把默认值写回去。

- **仍然是整机安装**：官方 MSI 是 `ALLUSERS=1`，装到 D 盘一样要过 UAC —— 权限这件事不因换盘而改变。
- **只对「首次安装」生效**：「Node 版本过低 → 一键升级」那条路**不开放**换目录 —— 同一个 ProductCode 在升级时改 `INSTALLDIR` 会留下旧目录与旧的 PATH 条目。真要换盘，先卸载 Node.js 再重装。
- **装完会核对**：MSI 对拼错/不认识的属性是**静默忽略**的（照样返回 0），所以安装后程序会确认 `node.exe` 真的落在指定目录里；没落进去就如实报错，而不是弹一个「安装成功」骗人。
- **路径会被校验**：绝对路径、无 `..`、盘符必须存在、不含 `< > " | ? *`、不落进 `Windows` / `ProgramData`、不直接装到 `Program Files` 根目录、长度上限 200 字符。不合法会当场拒绝，而且**不会先下载那 30MB**。

### 引导安装 DSH 的安装位置

「缺少 DSH」这一步同样有一个**安装位置**输入框，默认已填好 **npm 的全局目录**（程序问一次 `npm config get prefix`，问不到才回落 `%APPDATA%\npm`；通常就是 `C:\Users\<用户名>\AppData\Roaming\npm`，也就是 DSH 现在这个位置）。想装到别的盘，改成 `D:\dsh` 之类即可，也可以点「浏览」选文件夹；清空则回到 npm 自己的默认目录。

它最终以 `--prefix <目录>` 交给 npm。**注意这不是 Node 那种整机安装**：不需要管理员权限（目录是当前用户可写的就行），代价是「npm 全局目录」本来是所有全局包共用的 —— 以后你在终端里 `npm install -g <别的包>` 仍然会装到 npm 的默认目录，两份并存、互不影响。

几条要注意的：

- **装完会把该目录写进你的用户 PATH**（`HKCU\Environment` 的 `Path`，保持 `REG_EXPAND_SZ`，不碰系统 PATH、不需要管理员）：这样终端里也能直接敲 `dsh`，本程序以后也检测得到它。当默认位置本来就在 PATH 里时什么都不改。写不进去（极少见，例如注册表被策略锁定）会如实提示，而不是假装成功 —— 程序自己用完整路径启动 DSH，不受影响。
- **装完会核对落点**：npm 的退出码 0 只代表它自己认为成功，所以安装后程序确认 `dsh.cmd` 真的在指定目录里；没落进去就报错，并附上实际检测到的位置。
- **更新装回原地**：「更新 DSH」不再固定装到默认目录，而是按 `dsh.cmd` **实际所在**的目录加 `--prefix` 更新 —— 否则机器上会留下第二份 DSH，检测到哪一份变成看运气。
- **用户改过的值不会被覆盖**：与 Node 那条一致，一旦手动改过（或「浏览」选过），点「重新检测」不会把默认值写回去。
- **路径会被校验**：绝对路径、无 `..`、盘符必须存在、不含 `< > " | ? *`、不落进 `Windows` / `ProgramData`、不直接装到 `Program Files` 根目录、长度上限 200 字符；并且**不能含 `%` `!`** —— 这个值要经 `cmd.exe` 交给 `npm.cmd`，而 cmd 在双引号内仍会展开 `%VAR%`、开启延迟展开时 `!` 另有含义，无法可靠转义，只能拒绝。
- **目录会被自动创建**：npm 对不存在的 `--prefix` 会直接以 `ENOENT … lstat` 失败（它不像 MSI 那样替你创建 prefix），所以程序先建目录，建不了就明确报错。

## Node.js 版本检查

DSH 的运行下限是 **Node.js 22.19.0**：SQLite 会话存储用的 `node:sqlite` 在 22.13 才去掉实验标记，原生 TypeScript type-stripping 在 22.18 才默认开启，另有一个依赖（`@earendil-works/pi-ai`）自己声明 `engines.node >=22.19.0`。而**已发布的 `@deepseek-ai/dsh` 包并不声明 engines**，所以在旧版 Node 上 npm 照装不误，问题只在运行时暴露（例如 Node 21.7.3 上 DSH 根本起不来）。

本程序因此把检测到的 `node --version` 与这条下限比较，把「看不懂的启动失败」变成一道可决策的提示。**Node 的版本与安装决定统一收在首次运行向导里**——首选项里没有 Node 一行，之后要升级就直接用官方安装包：

| 位置 | 行为 |
|---|---|
| 首次运行向导 | Node.js 一行显示 **⚠ 版本过低** 与 `21.7.3 → v22.19.0+`，并给出告警面板：**一键下载并安装最新 LTS**（与「缺少 Node」同一套 SHA-256 校验过的官方 MSI 流程）、**自行到官网下载安装**、**重新检测**、**保留该版本，仍要继续**。向导只在首次运行时出现（`config.json` 一存在就不再出现），所以这是做这类决定的地方。 |
| 点「启动」 | 直接拒绝并把原因说清楚（「检测到 21.7.3，DSH 要求 v22.19.0 或更高」），并指到官方 LTS 安装包，不再让 DSH 闪退后甩一段看不懂的错误。 |

- **「保留该版本，仍要继续」** 写入 `config.json` 的 `node_min_ack`（只动这一个键，读取-修改-写回，不重写你的其它设置），并关闭启动拦截。它记录的是**你当时接受的那条下限**：程序以后提高要求会重新提示，而不是永久关掉。这是向导里的一次性决定，界面里没有再打开/关闭它的开关。
- **版本号绝不猜。** 没装 Node、`node --version` 读不到、版本串解析不了，一律记为 `? 无法判定`——会提示，但**不会**拦截启动：读不出版本号不等于运行时坏了。
- **升级不会连累 DSH。** 官方 MSI 会覆盖原目录里的 Node.js（PATH 不变），DSH 的全局命令在用户 npm 目录，因此引导升级不需要重装 DSH。若安装程序退出后版本号看起来还没变，重启本程序（PATH 可能需重启才刷新）后再点「重新检测」。

## 安装（Installation）

如果不想从源码安装，可以直接从以下链接下载现成的 **Windows 10/11 安装包**（DSH-Desktop-windows-nsis.zip）：

- <https://github.com/White-Egret/DSH-Desktop/releases>

或

- <https://tfevx3uq.qwenwork.host/DSH-Desktop-windows-nsis>

无需本地 Rust 环境——GitHub Actions 云端构建（见下一节）。取最新成功构建的产物：

- `DSH-Desktop-windows-nsis` → 内含 `DSH Desktop_<版本>_x64-setup.exe`（NSIS 安装包，推荐）
- `DSH-Desktop-windows-msi` → MSI 安装包
- `DSH-Desktop-windows-portable-exe` → 免安装独立 exe

用 NSIS 安装包安装或直接运行便携 exe。首次启动会出现一次环境检查向导；一旦 `%APPDATA%\com.dsh.desktop\config.json` 存在即不再出现。

**下载后请校验。** 每次构建都会产出一份 `SHA256SUMS.txt` —— 维护者把它放进 Release 时它就随 Release 一起 —— **以及**针对该次运行全部产物记录的一份签名「构建来源证明」。两者都出自**构建流程本身**，而不是把文件交给你的人；这正是关键：文件可以从任何渠道拿到，但校验要拿文件所在主机**控制不了**的源来比对。同一份校验值也会打印在每次构建日志末尾（「生成 SHA-256 校验清单」那一步），什么都不用下载就能直接读到。

```powershell
# 1) 哈希校验：与该文件在 SHA256SUMS.txt 中对应的一行比对（不区分大小写）
Get-FileHash .\DSH-Desktop-windows-nsis.zip -Algorithm SHA256

# 2) 更强的一道：证明这个二进制确实出自本仓库的 build-windows.yml
#    （需 GitHub CLI；对解压出来的 .exe 执行）
gh attestation verify ".\DSH Desktop_<版本号>_x64-setup.exe" --repo White-Egret/DSH-Desktop   # 去掉尖括号
```

第 2 项是由 Sigstore 签名的声明，把文件的哈希与本仓库、本 workflow 文件、以及构建它的那个具体 commit 绑在一起，因此**不需要事先信任任何我们贴出来的字符串**。它作用于安装包/便携 exe 本身（`gh` 校验的是文件而不是压缩包，先解压），并且存放在那次 workflow 运行里、而不是 Release 页面上。

上面两道校验对从镜像下载的文件同样有效，而这正是那个镜像可以继续放心用的原因：它存的是同一批构建产物的**逐字节相同**的副本。`gh` 是按文件的摘要去查证 attestation 的，因此不关心你从哪里拿到文件 —— 反过来，向镜像索取它**自己**的校验值则毫无意义：被换掉的文件和被换掉的校验值会一起送过来。

> 这些产物**没有代码签名**，所以首次运行时 Windows SmartScreen 会提示"未知发布者"（部分受管企业电脑甚至会直接拒绝运行未签名的可执行文件）。为什么这不是"买张证书"就能解决：代码签名证明的是**谁发布的**这个文件，而哈希证明不了这一点；EV 证书自 2024 年起**不再**免检直达，也就是说所有方案（包括付费的）都要从零信誉开始、靠一次次发布累积；而最便宜的托管签名服务（Azure Artifact Signing，约 $9.99/月）对个人开发者只开放美国与加拿大。对这类项目而言免费的路子是 [SignPath Foundation](https://signpath.io)（为符合条件的开源项目提供代码签名），目前正在评估。在那之前，上面这两道校验才是你确认"文件就是本仓库构建出来的那一个"的依据。

**默认安装到哪里。** NSIS 安装包的默认目录是 **`C:\Users\<用户名>\DSH Desktop`**（当前用户安装，不需要管理员权限），安装时的「选择安装位置」页仍可改成任意目录。**升级安装沿用原路径**：安装程序会从注册表读取上次的安装位置并继续用它，因此不会在新默认目录下多出一份。MSI 是另一套「整机安装」包，默认目录仍是 `C:\Program Files\DSH Desktop`。

> 这个默认值来自一份「随仓库保存」的 Tauri NSIS 模板（`src-tauri/nsis/installer.nsi`，通过 `bundle.windows.nsis.template` 接入）：Tauri 没有「默认安装目录」配置项（[tauri-apps/tauri#11015](https://github.com/tauri-apps/tauri/issues/11015)），而 NSIS 是在 `.onInit` 里定死这个值的，安装钩子（installer_hooks）执行得太晚、改不到默认值。该文件是**脚本生成、不要手改**：`node scripts/gen-nsis-template.mjs` 会按 `package-lock.json` 里**锁定的** `@tauri-apps/cli` 版本取对应官方模板，只打这一个补丁；升级 CLI 后重跑一次，模板就不会与 bundler 悄悄脱节。

### npm 缓存位置

Windows 上 npm 默认把缓存放在 **`%LOCALAPPDATA%\npm-cache`**（`C:\Users\<用户名>\AppData\Local\npm-cache`；Linux/macOS 是 `~/.npm`）。它和全局目录（`%APPDATA%\npm`）是两处不同的地方，`DSH 安装位置`改的是后者、动不到它 —— 所以缓存单独给了这一项，想把它挪到别的盘（或搬回来）就在这里填 / 清空。首选项里那一项旁边会显示两件事：**npm 配置里的值**与**实际生效的值**（被环境变量或项目级 `.npmrc` 覆盖时两者会不同，会明确标出 ⚠）。

这一项的做法与其它字段有一处本质区别：**它改的是 npm 自己的文件**。

- **落点是 `~/.npmrc` 的 `cache=` 一行**（文件路径问 `npm config get userconfig`，不是猜的），所以终端里的 npm 也会用这个位置；本程序代跑的 npm（装/更新 DSH、包列表、版本查询）**另外显式带 `--cache <目录>`**，这样日志里那行命令复制出来行为完全一致。
- **只动那一行，其余内容逐字保留**：注释、`registry=`、`_authToken=` … 全部原样（用「最小行编辑 + 原子替换」，与改 DSH `settings.yaml` 时同一条原则）。这里刻意**不调 `npm config set`** —— 实测 npm 的 ini writer 会把文件里的注释吃掉。
- **留空 = 删掉那一行**，npm 回到默认位置（不是"设成默认值"，配置里不留痕）。
- **值限制**：绝对路径、无 `..`、盘符必须存在、不含 `< > " | ? *`、不落进 `Windows` / `ProgramData`、不能含 `%` `!`（要经 cmd.exe）、**不能含 `#` `;`**（npm 的 ini 把这两个字符当注释起点，实测 `cache=D:\a#b` 会被读成 `D:\a` —— 静默指向另一个目录），长度上限 **100 字符**：npm 会在缓存根之下再写 158 个字符的内容寻址路径（实测），超过经典 260 上限后资源管理器 / PowerShell 就删不动那棵树了（npm 自己还能写，但"清不掉"是更糟的结局）。
- **目录不由程序创建**：npm 会自己建（实测指向一个还不存在的目录也能装上）。

### 参数与路径策略（保存时校验，每次使用时再校验一次）

这些配置项不是「一段文字」，而是能力：`dsh_path` / `npm_path` 会被**执行**；`extra_args` / `package_name` 会成为命令行参数；而 **DSH 家目录的上一级会被当作 DSH 进程的工作目录**（同时也是 `npm` 读取 `./.npmrc` 的位置）。由于 `config.json` 是明文的当前用户文件、且开机自启会静默按它执行，因此校验发生在**每一次使用点**，不只是点「保存」时。

- **参数**：拒绝 shell 元字符（`& | < > ^ % !` 与引号）。因为 `cmd.exe` 会对整条命令行二次解析，`a&calc.exe` 会变成两条命令。普通参数（`--host=127.0.0.1`、`--port`、`--no-open`、路径等）不受影响。
- **所有路径**：必须是带驱动器的绝对路径；拒绝 `\\服务器\共享`（UNC）—— 往共享写会触发 NTLM 认证而外泄凭据，从共享执行程序等于把可执行文件交给对端；拒绝含 `..` 的路径（直接拒绝而不是折叠规范化，否则 `C:\Windows\..\x` 会被洗白成合法路径）。
- **程序路径**：扩展名必须是 `.exe` / `.cmd` / `.bat`（`.ps1` 或无扩展名会走不可预测的文件关联），启动时文件必须真实存在，且不能位于 `%TEMP%` 内。
- **执行方式**：`.exe` 直接走 `CreateProcess`，链路上根本没有 `cmd.exe`；`.cmd` / `.bat` 这类 shim 只能经 `cmd.exe`，所以命令行由本程序自己拼装并逐令牌加引号，不依赖默认的字符串转义。
- **家目录**：不能是驱动器根目录、不能是用户目录本身或它的任一层父目录、不能在 `Windows` / `Program Files` / `ProgramData` 内。（Node.js 本身仍可以正常装在 `Program Files` —— 该限制只针对家目录。）
- 路径会被规范化后写回，磁盘上保留的就是通过校验的形态。

任一项不通过时，程序会拒绝启动/更新并在状态区显示原因 —— 被手改或被植入的 `config.json` 无法把「点一下启动」变成执行另一个程序。

### Webview 隔离与 CSP

DSH 网页界面属于不可信内容（它渲染模型输出），却以第二个原生 webview（label=`dsh`）的形式内嵌在主窗口的工具栏下方。有两条彼此独立的机制把它挡在特权面之外：

- **capability 用 `webviews` 绑定，而不是 `windows`。** Tauri v2 中，`windows` 一旦命中窗口标签，就会对该窗口内的**每一个 webview** 生效 —— 所以写 `windows: ["main"]` 等于把 `core:*` 同时发给内嵌的 DSH 页面。因此 `capabilities/default.json` 只列 `"webviews": ["main"]`（启动器自身的 webview），并刻意不写 `windows`，这也是官方对多 webview 窗口的建议。
- **它的 origin 属于 remote。** 内嵌页面加载的是 `http://127.0.0.1:<port>`，Tauri 将其判定为远程来源，而远程来源默认无法触达 `invoke_handler` 里的自定义命令，除非某个 capability 在 `remote.urls` 中显式放行。**永远不要给 `dsh` 这个 webview 加这种放行** —— 隔离成立靠的就是这一条加上面的作用域绑定。

启动器自身页面运行在严格 CSP 下（`script-src 'self'`，不允许 `unsafe-inline`/`unsafe-eval`，`object-src 'none'`、`base-uri 'none'`、`form-action 'none'`、`frame-src 'none'`（不可信内容无法被拉进特权文档）），资源协议（asset protocol）关闭。所有不可信字符串 —— DSH 输出、错误信息、检测到的路径 —— 一律用 `textContent` 渲染，绝不拼成 HTML。此外 Tauri 会在编译期为自身资源注入 nonce/hash，所以 `script-src 'self'` 无需放宽即可正常工作。

- **`freezePrototype` 是 `false`，这是有意为之、不是漏配。** 上游的 `freezePrototype` 加固会给**每一个** webview（包括内嵌的 DSH 页面）注入一段冻结 `Object.prototype` 的脚本，而 DSH 前端在它之下会坏掉：Monaco 主题服务会以 strict mode 给一个继承属性赋值（`target.constructor = …`），原型被冻结后抛 `TypeError: Cannot assign to read only property 'constructor'`，把会话渲染槽整体打崩 —— 表现为回复闪一下然后消失，而同一个页面在普通浏览器里完全正常。该加固的本义是防原型污染攻击被注入的 IPC 桥，但 `dsh` 这个 webview 没有任何 capability，本页面又是全本地静态页、从不把不可信文本变成 HTML，所以冻结在这里只有副作用、没有防护价值，故全局关闭。**请勿重新打开**；若未来 Tauri 提供按 webview 豁免该脚本的 API，可再评估只对 `dsh` 关闭。

> 桌面外壳的 CSP 与原型冻结，**保护不了 DSH 自己的 Web 应用**。任何渲染不可信模型输出的页面，在它自己的 origin 里就是注入目标 —— 对应的防线（每个插值都转义、绝不把数据拼成代码、让会话令牌不可被读取）必须落在 DSH 的 Web 应用里。

> Tauri 是以「往构建后的 HTML 里注入 `<meta http-equiv="Content-Security-Policy">` 标签」的方式下发这份策略的（见 `tauri-utils/src/html.rs` 的 `create_csp_meta_tag`），而不是 HTTP 响应头。按 CSP 规范，`<meta>` 里的 `frame-ancestors`、`sandbox`、`report-uri` 会被浏览器忽略，所以上面刻意没有列它们 —— 列出的每一条都是真正生效的。若将来确实需要防内嵌，得改用 `app.security.headers` 以 HTTP 头下发。

### 会话令牌的落盘与日志

DSH 的 next 频道会把监听地址打印成 `http://127.0.0.1:<端口>/?token=<base64url>`。这个 token 能换取 30 天有效期的签名 cookie —— 它就是你的 DSH 会话身份 —— 所以启动器把它当**凭据**看，而不是 URL 上无关紧要的一部分。

它仍然会被记住：**连接现有服务** 与 **页面重开** 这两个场景读不到任何进程输出，不记住就得让你重新认证一次。1.2.6（安全审查 M-2）改动的是「记住的东西在磁盘上不再可读」：

- **`config.json` 里存的是密文。** 地址先用 Windows DPAPI 加密（`CryptProtectData`，**CurrentUser** 作用域，另加一串应用专属熵），再以十六进制写进 `last_url_enc`。≤ 1.2.5 写在 `last_url` 里的明文会在下次启动时迁移成密文键，明文键随之删除。被手改或解不开的密文一律当「没有记录」（页面回落到裸 `http://127.0.0.1:<端口>`），而且**没有任何一条失败路径会回落成写明文** —— 加密失败就这次不记地址。DPAPI 是 Windows 的能力，本启动器也只发布 Windows 版。
- **日志里的值被脱敏。** 上面那个地址是 DSH 自己打到 stdout 的，原文会进 `desktop.log`、`<家目录>\logs\dsh.log` 和日志面板（面板上的「复制日志 / 复制错误信息」还能把它一键拷进剪贴板）。现在所有行在**写入文件、进面板、进剪贴板之前**统一过一道脱敏：任何 `token=` 参数的值都换成 `***`（你会看到 `?token=***`）。输出里的其它内容一字不改。
- **这层防护覆盖到哪、覆盖不到哪。** DPAPI 把密文绑定到你的 Windows 用户账户：同机上的其他用户、把文件拷出磁盘（备份、同步目录、支持包、截图）或整盘镜像都读不到它。但它**挡不住以你自己身份运行的其他进程** —— 熵是编译在二进制里的常量、不是秘密，你这次会话里的任何代码都能让 DPAPI 解密。「本用户下已经跑起来的恶意程序」不在这层防护的射程内；另外 DSH 自己仍然在进程内存里持有该令牌，换取到的会话 cookie 也存在 WebView2 的 profile 目录里。

### 配置写盘是原子的

`config.json`、`ui-language` sidecar 与 DSH 的 `settings.yaml` 现在统一**原子写盘**（安全审查 L-6）：新内容先写进**同一目录**下的临时文件，`fsync` 落盘后再用 `rename` 覆盖目标。这样崩溃 / 断电 / 被杀进程发生在中间时，磁盘上留下的是**改动前的那份完整文件**，而不是半截文件。这一点必须做，是因为旧实现是直接覆盖写（本质是「打开 + 截断 + 写入」三步），而半截 `config.json` 会被加载侧的 `unwrap_or_default()` 静默吞掉 —— 也就是「崩一次 = 所有设置被抹掉」。

- 临时文件用 `create_new` 创建：名字已存在时（可能是别人预置的符号链接）**直接失败**，绝不顺着链接写到别处去。它还必须与目标**同目录** —— `rename` 只在同卷内是原子替换，把临时文件丢到 `%TEMP%` 就完全失去意义了。
- 最后一步 `rename` 若被杀毒 / 备份 / 同步工具占住目标文件而失败，会做几次有界重试，仍失败就如实报成一次普通的写入失败。**绝不退化成非原子的直接覆盖**。需要说明的是：这是个健壮性修复、不是权限边界 —— 它消灭的失败模式是「丢设置」，不是「提权」。
- 将来移植到 Unix 时：当前几个调用点写的都不是敏感内容，用默认权限即可；若某个调用点需要 `0600`，必须先 `set_permissions` 再 `rename`（替换文件会换掉 inode，原权限位不会自动继承）。

### 用系统浏览器打开链接

`open_in_browser`（首次运行向导、关于 / 帮助链接用到）改为把 URL 交给 `rundll32 url.dll,FileProtocolHandler`，不再用 `explorer <url>`（安全审查 L-5）。两者都是把 URL 作为真正的 argv 元素直传、都不经过 shell，但 `explorer` 首先是个文件管理器、其次才是协议启动器，它对含特殊字符 URL 的解析规则不如前者可预期；`rundll32 url.dll,FileProtocolHandler` 则直接走 `ShellExecute` 的 URL 处理路径。

`rundll32.exe` 还一律用 `%SystemRoot%\System32` 的**绝对路径**启动。`CreateProcess` 的搜索顺序里「当前目录」排在系统目录之前，裸名字等于把「往启动器自己的工作目录里放一个同名 exe」变成一条可执行路径 —— 没有任何理由为这行代码留这个口子。读不到 `%SystemRoot%` 时退回裸名，而不是干脆打不开链接；两种情况下都只放行 `http://` 与 `https://`。

## 界面语言（Language）

启动器界面支持简体中文 / English 双语：

- 在 **⚙ 首选项 → 语言 / Language** 选择后保存：工具栏、状态区、弹窗、托盘菜单与所有启动器日志即时切换（无需重启 Desktop；重启后同样按配置生效）。选回「中文」即全部恢复中文。
- **DSH 自身界面**：保存时程序会把对应值写入 `<DSH 家目录>\settings.yaml`：

  ```yaml
  locale:
    preference: zh   # 或 en
  ```

  写入采用最小改动方式，只增改 `locale.preference`，不会破坏该文件中的其他配置。DSH 启动时读取此文件，因此**需重启 DSH**（工具栏「⟳ 重启」）其界面语言才会变化；DSH 正在运行时切换语言，日志中会给出提示。
- DSH 的原始 stdout/stderr 与 npm 输出属于第三方程序内容，日志中原样呈现、不做翻译。

## 外观（Appearance：浅色 / 深色 / 跟随系统）

与 DSH 设置页「通用设置 → 外观」同一套语义，桌面端与 DSH 页面联动：

- 在 **⚙ 首选项 → 外观** 选择后保存：工具栏、状态区、弹窗、向导与原生标题栏即时换肤；「跟随系统」会订阅系统的深浅反转并实时响应（无需重启 Desktop；重启后同样按配置生效）。
- **DSH 页面实时跟随**：保存时程序把对应值写入 `<DSH 家目录>\settings.yaml`：

  ```yaml
  ui-theme:
    preference: light   # 或 dark / system（同级的 fontSize 等其他键原样保留）
  ```

  DSH 的 settings-file 提供器监视该文件并把变化推送给已打开的页面，因此**无需重启 DSH**，页面即刻换肤（区别于界面语言需要重启才变化）。
- 写入同样是最小改动方式，只增改 `ui-theme.preference`，不破坏其他配置。
- 升级兼容：老版本 `config.json` 没有外观字段时，首次加载会读取 DSH `settings.yaml` 的现有主题作为桌面端初值，升级本身不会改变 DSH 页面的外观；此后在桌面端保存即接管该值。
- 在 DSH 页面自己的设置里改外观只影响 DSH 端；桌面端以上一次「保存」的选择为准。

## 工具栏显示模式（Toolbar: pinned / auto-hide）

顶部那条工具栏有两种显示模式，在 **⚙ 首选项 → 自动隐藏工具栏** 里切换。选择写入 `config.json` 的 `toolbar_mode`（`pinned` / `auto`），下次启动按配置生效：

- **固定显示（`pinned`，默认）**：工具栏始终可见，内嵌 DSH 页面位于其下方。历史行为，也是从旧版本升级后的默认值，升级本身不改变使用手感。
- **自动隐藏（`auto`）**：工具栏默认收起在窗口之上，内嵌页面**占满整个窗口高度**；鼠标移到窗口顶部 8px 的触发条时工具栏滑出，鼠标离开工具栏 500ms 后收回。

**快捷键**：`Ctrl+Shift+H` 在两个模式间切换。注意它只在本启动器页面持有键盘焦点时有效 —— 焦点落在内嵌 DSH 页面里时按键由 DSH 自己处理，此时把鼠标移到窗口最顶部即可唤出工具栏。

**动画**：只用 `transform: translateY(-100%)` ↔ `translateY(0)` 配合 `transition: transform 0.25s ease-in-out`，**不动 `top` / `height` / `margin`**，所以走合成器线程、不逐帧触发重排。自动隐藏模式下工具栏带一层轻微投影，滑出时与内容区之间才有层次。

**实现原理（为什么不干脆用 CSS 叠层）**：内嵌的 DSH 页面不是 `<iframe>`，而是 Tauri 的**原生子 webview**——Z 序永远在启动器页面之上，位置与尺寸只能由 Rust 侧设置，没有任何 CSS 手段能让它给悬浮工具栏让位。于是这里的做法是让内容区**真的**铺满整窗，由外壳把工具栏画在它上方：

1. 前端通过命令 `set_toolbar_hidden` 把「工具栏是否隐藏」告诉 Rust；
2. Rust 用纯函数 `content_offset_for(模式, 是否安全模式, 是否隐藏)` 算出内嵌 webview 的 Y 偏移（固定 / 安全模式 = 工具栏高度 43.2px，自动隐藏且收起 = `0`），并同步它的位置**与高度**。**高度 = 客户区高 − 该偏移**，因此 `偏移 + 高度 == 客户区高` 在构造上恒成立。内嵌的是原生子窗口：若给它整窗高，底边就会越过父客户区 43.2px，而 Windows 裁掉的正是**页面底部可见的内容**，WebView2 却仍按拿到的高度布局，于是页面底部永远滚不到。这条不变量由纯函数 `content_height(client_h, top)` 及其 Rust 单测钉死；
3. 收起后网页顶部 8px 会被子 webview 覆盖，鼠标事件到不了启动器页面，因此**由外壳读系统光标位置兜底**：前端每 120ms 调一次 `probe_toolbar_hotzone`，Rust 侧取 `GetCursorPos` 的屏幕坐标、减去客户区原点、除以缩放比，判断光标是否回到顶部触发条内。这只是收起状态下的兜底轮询，鼠标在工具栏上时完全走普通 DOM 事件（`mouseenter` / `mouseleave`）。

另外两点：工具栏上的下拉菜单 / 弹窗打开期间禁止自动隐藏，否则菜单会连同工具栏一起滑走；收起是**两段式**的——先滑上去，260ms 动画走完后再把内容区扩到整窗，这段时间里鼠标回到顶部会取消收起。

**安全模式恒为固定显示（硬约束）**：「退出安全模式」按钮与琥珀色徽标就长在工具栏上，把它藏起来等于把用户困在安全模式里。因此做了四重保障：

- Rust 侧 `content_offset_for` 把 `safe_mode` 放在**最先短路的判断分支**；
- 命令 `set_toolbar_hidden` 做 `hidden && !is_active` 运算，并把**实际生效值**回传给前端用于纠偏；
- 进入安全模式时调用 `force_toolbar_shown` 清掉任何残留的收起状态；
- 前端首选项里的开关在安全模式下禁用，并提示「安全模式强制固定显示」。

**还有一处注意**：自动隐藏只在「DSH 页面已经就绪」时才真正生效。DSH 尚未启动 / 尚未就绪时，状态区就是全部内容，工具栏必须留着，所以此时仍按固定显示处理——若觉得「开了开关却没自动隐藏」，先看 DSH 是否已经跑起来。

## 窗口布局记忆（Window layout）

记住主窗口的**大小、位置与最大化状态**，下次启动原样恢复。用 Tauri 官方的 `tauri-plugin-window-state` 实现，**不自己写事件防抖 + JSON 读写**。

- **为什么必须是官方插件**：自研方案的坑不在保存、在**恢复** —— 显示器拔掉之后，磁盘上留下的坐标可能落在已不存在的屏上，窗口开出来在可见区域之外，用户只能去删配置文件。该插件恢复时会遍历当前显示器，只在某个显示器与「保存的位置 + 尺寸」**相交**时才套用坐标，这正是那条 Bug 的官方修法。本程序这边只负责「什么时候不该记」。
- **记哪三样**：`POSITION | SIZE | MAXIMIZED`。**刻意不记可见性（VISIBLE）** —— 默认「点 X 隐藏到托盘」，若把可见性也记下来，下次启动会恢复成「隐藏」，表现为托盘图标点不开窗口（正是 `show_main_window` 那套重绘兜底要救的故障）。装饰与全屏同样跟随 `tauri.conf.json`，不被历史状态改写。
- **状态文件**：`%APPDATA%\com.dsh.desktop\.window-state.json`（调用 `tauri-plugin-window-state` 的默认位置）。想「重置窗口布局」时，**先关掉本程序再删掉这个文件**，下次启动即回到 `tauri.conf.json` 的 1376×774 居中。文件内容损坏（手工改错、截断）会被当作「没有记录」，不会导致启动失败 —— 这也是不必手工清理历史文件的原因：格式不认识就等于没有。
- **安全模式完全不受影响**：进入安全模式会把日常 DSH 实例**整棵停掉**，再以独立家目录（`.dsh-safe`、3081 端口）全新启动一个安全实例 —— 在运行环境这一层就是一次干净的重新启动；但**桌面窗口不会重启**（仍是同一个窗口），所以两条路径分别做了隔离：以安全模式专用入口（`--safe` / `--safe-mode` / `DSH_SAFE_MODE=1`）启动时既不恢复也不保存；点按钮进入时先冻结日常布局（快照 + 落盘），再把窗口**重置为 `tauri.conf.json` 的默认几何**，安全模式期间无论怎么拖、怎么缩都不会写进磁盘，退出时日常布局原样回来。详见下节。
- 窗口尺寸按**物理像素**记录，位置在恢复时按当前显示器校验 —— 所以换 DPI、换显示器之后尺寸不会越用越走样。

## 默认端口（Default port）

- 默认端口为 **3080**。
- 可在首选项页修改；启动命令、健康检查轮询、内嵌 WebView 加载地址全部跟随配置端口。
- 示例：`http://127.0.0.1:3080`、`dsh web --port 3080`。
- 每次启动前检测端口占用；被占用时**绝不强杀未知进程**，面板提供「连接现有服务」「修改端口」「重新检测」。若 DSH 输出中给出不同实际地址（如 `dsh web: http://127.0.0.1:3080`），以实际地址优先加载。

## 版本频道检测（latest vs next）

程序用**一条命令**同时取回两个 npm dist-tag：

```text
npm view @deepseek-ai/dsh dist-tags
→ { next: '0.2.0-rc.1', latest: '0.1.0', … }
```

`latest` 是当前对所有用户发布的**稳定版**；`next` 是**下一版的 beta**——版本号比 `latest` 更新，用于提前试用与收集反馈，可能带不兼容改动。弹窗在两个选项之上就把这层含义写明了，不留给用户猜。程序把本地已装版本与两者中的「最新」比较（**两标签都存在且不同 → 以 next 为准；否则以 latest 为准**）：

| 状态栏显示 | 含义 |
|---|---|
| `0.2.0-rc.1（已是最新）` | 已装的就是两个频道里最新的那个，无需更新 |
| `0.1.0 → 0.2.0-rc.1` + 「可更新 next」 | next 比已装版本更新（且 next ≠ latest） |
| `0.1.0 → 0.1.5` + 「可更新」 | latest 有新版；该包没有独立的 next 频道（或 next 与 latest 相同） |
| `0.1.0（更新状态未知）` | 本地版本读到了，但 registry 查询失败（原因写进日志） |
| `未知` | 本地版本都读不到，无从比较 |

检测在每次程序启动、以及 DSH 服务启动/重启后自动进行，并带 60 秒冷却，不会反复敲 registry —— 因此没有也不需要「手动检查版本」按钮。两个频道的原始版本号都会写进日志。

## 更新 DSH（Update DSH）

点工具栏「⤓ 更新 DSH」→ 弹窗里列出 **latest 与 next 两个频道及其当前版本号** → 选一个 → 确认 → 停止服务 → 执行安装 → 成功后自动重启 DSH。

**不论现在装的是哪个版本，两个频道都可以任选。** 想试更新的东西就选 `next`，想退回旧的稳定版就选 `latest`：弹窗不会因为「你已经装了某个版本」而禁用任何一个选项。最终执行哪条命令完全由你的选择决定：

| 频道 | 实际执行的命令 |
|---|---|
| `latest`（稳定版） | `"<npm>" install -g @deepseek-ai/dsh@latest` |
| `next`（下一版的 beta，更新） | `"<npm>" install -g @deepseek-ai/dsh@next` |

- 弹窗默认选中**较新的那个频道**（也就是状态栏指向的那个），因为点「更新」的人通常就是要最新版。已装最新版时**不会**默认帮你选另一个频道——那等于替你偷偷做了降级，代价比「原地重装一次」大得多；另一个频道就在下面一格，点一下即可，并且带着自己的版本号与「较旧」标记。
- 每个参数都作为独立 token 传给 npm（见「参数与路径策略」）。频道本身**不是可配置项**：后端只接受字面量 `latest` 与 `next`，其余一律拒绝，所以这个选择框无法被当作参数注入的入口。具体版本号由 npm 在安装时向 registry 解析，所以即使某个频道的版本号显示为「未知」（查询失败），也照样可以选择安装。
- **⚠ 无论升级还是退回，都请先备份 DSH 家目录（默认 `%USERPROFILE%\.dsh`）。** 弹窗里显示的是你当前**实际配置**的路径，日志在安装开始时还会再提醒一次：新版本可能改写配置/会话格式；而退回旧版本同样可能读不懂新版本写下的东西。
- 安装期间**页面中央实时显示进度**（「已获取 N 个包文件 / 用时」+ npm 输出滚动，同时写入日志，来源标记 `update`）；期间其他按钮禁用。
- 「检测全局包名」（`npm list -g --depth=0`）可确认包名。

## 安全模式（Safe Mode）

类似操作系统的安全模式：用一个**独立、纯净的家目录**启动 DSH，专门用来检查和修复日常模式环境的问题。入口是工具栏「更新 DSH」与「日志」之间的「🛡 安全模式」按钮。

**机制**：等价于 `DSH_HOME="%USERPROFILE%\.dsh-safe" dsh web --port 3081 --no-open`。`.dsh-safe` 与日常 `.dsh` 平级（不放 app_data_dir）；DSH 在「家目录里除凭据文件外全空」时会自动重建全部原厂配置。

**进入流程**（点一下按钮，全程日志可见）：

1. **预检**：先完整停掉日常实例（`taskkill /T` 带走 node 子进程）并确认日常端口已释放、3081 空闲；任何一项不满足都**提示并拒绝进入，绝不强行**（更新进行中同样拒绝）。
2. **基线重置**（首选项开关，**默认关闭**）：关闭时**沿用**已有的 `.dsh-safe`——上一轮安全模式的配置与日志保留下来；开启时把已存在的 `.dsh-safe` 整目录重命名为 `.dsh-safe-archive-<YYYYMMDD-HHMMSS>` **归档（绝不删除）**，再重建空目录，从而让每次进入都是恒定的原厂基线。首次进入（目录还不存在）两条路径结果相同：都是只含凭据的空家目录。
3. **凭据借用**：把日常家目录的 `.credentials.yaml` **覆盖拷贝**进 `.dsh-safe`（每次进入都重新拷，保证拿到当前有效密钥）。这是唯一被拷贝的文件；源文件缺失/为空不阻塞进入（横幅提示，DSH 走首跑流程）。**内容不写任何日志、不经 IPC 给前端、不进环境变量**；Unix 下收紧为 0600。
4. **启动**：spawn 子进程（额外注入 `DSH_DAILY_HOME=<日常家目录>`，让修复 agent 天然知道修复目标；只有路径，绝无密钥），复用日常模式同一套输出解析 / 就绪等待 / 页面内嵌逻辑加载 3081 的认证 URL。

**视觉区分**：窗口标题加「[安全模式]」前缀，工具栏切换琥珀色并显示「🛡 安全模式」徽标；进入后弹出引导横幅（当前处于安全模式 / 日常家目录路径 / 凭据借用结果三件事）。安全模式下日常控制按钮禁用；工具栏也**强制固定显示**，首选项里的「自动隐藏工具栏」在这期间不生效 —— 退出按钮与徽标就在工具栏上，收起它等于把人困在安全模式里（见「工具栏显示模式」）。

> 琥珀标记是**立即**落上的，不存在「刚进安全模式时工具栏还是灰的、点一下才亮」这种中间态。这里曾经有过一段竞态：安全实例就绪时外壳先广播「运行中」再挂载内嵌页面，前端会在收到「已进入安全模式」之前先按日常模式重算一次工具栏，于是工具栏按自动隐藏规则滑走、露出底下那条日常模式的浅灰底衬。现在改成状态一到就同步落标记（早于所有工具栏 / 按钮判定），另加一条纯 CSS 兜底（`body.safe-mode.tb-auto` 下强制工具栏留在原位、底衬直接隐藏），双保险。

**窗口布局**：窗口记忆与安全模式严格隔离。安全模式是一次独立环境的重新启动 —— 日常 DSH 实例被整棵停掉、安全实例用独立家目录在 3081 全新启动；但桌面外壳与窗口本身不重启，所以隔离由窗口记忆侧显式接管：进入时日常布局被冻结（快照 + 落盘）、窗口重置为 `tauri.conf.json` 的默认大小与位置；安全模式期间对窗口的任何拖动 / 缩放都**不会**写进磁盘；退出安全模式（含从安全模式直接退出程序）时，日常布局原样恢复。见「窗口布局记忆」。

**退出与修复验证闭环**：「退出安全模式」会 kill 安全实例（Child 句柄在 Tauri State 中，应用退出/窗口销毁同样兜底清理，强杀场景由 Job Object 在内核层结束进程树，绝不留孤儿进程占 3081），然后按日常模式既有路径重启；若日常实例在「修复验证等待」（默认 80 秒，首选项可调，0 = 关闭）内未就绪，提示「修复可能未成功」并提供一键**返回安全模式**。

**日志**：安全实例的输出实时进「日志」面板并落 `desktop.log`，但**不**往 `.dsh-safe` 里写镜像文件（保持「除凭据外全空」的原厂基线）。

## 日志（Logs）

两份日志都在用户目录下（无需管理员权限），超过 5MB 自动滚动为 `*.old`：

| 日志 | 路径 | 内容 |
|---|---|---|
| Desktop 日志 | `%APPDATA%\com.dsh.desktop\desktop.log` | launcher/update/setup 事件 + DSH stdout/stderr 镜像 |
| DSH 输出日志 | `%USERPROFILE%\.dsh\logs\dsh.log` | DSH 原始输出（跟随家目录设置：`<家目录>\logs\dsh.log`） |

UI 支持：「日志」实时面板（自动滚动/清空）、**打开日志目录**、**复制错误信息**（错误/端口占用状态下出现）、**复制日志**。DSH 的 stdout/stderr 绝不隐藏：实时进日志面板并同时写入上述两个文件 —— 唯一的例外是 DSH 认证地址里的会话令牌，它在进面板、进剪贴板、写进两个文件之前都会被脱敏成 `?token=***`（见[会话令牌的落盘与日志](#会话令牌的落盘与日志)）。

## 故障排查（Troubleshooting)

- **未找到 Node.js** — 到 <https://nodejs.org> 安装 LTS，装完重启本程序即可（首选项里的「自动检测」只用来刷新 npm / dsh 路径）。
- **未找到 npm** — 通常装好 Node.js 即有；npm.cmd 与 node.exe 同目录（如 `C:\Program Files\nodejs\npm.cmd`）。
- **未找到 DSH** — 执行 `npm install -g @deepseek-ai/dsh`（或用向导），或在首选项中指向已有 `dsh.cmd`（通常在 `%APPDATA%\npm\`；若向导里换过安装位置，就在你选的那个目录里）。
- **端口被占用** — 选「连接现有服务」（若是另一个 DSH 实例）、在首选项中修改端口、或在任务管理器自行处理占用进程；本程序绝不强杀。
- **DSH 启动超时** — 冷启动慢属正常；调大超时或设为 `0`（进程活着就一直等）。
- **DSH 启动后立即退出** — 看红色错误行（最后一条 stderr）与完整日志；常见原因：家目录配置错误、全局安装损坏、DSH 自身配置冲突。
- **配置路径无效** — 错误会给出具体路径；在首选项中修正即可（自动检测通常能修复）。
- **关了窗口还在运行** — 默认点 X 是隐藏到托盘；请用托盘菜单「退出」。可在首选项「点击窗口 X 时」修改行为。
- **托盘点不开窗口** — 现已实现 show/unminimize/set_focus + 重绘兜底；如仍遇到，请附 desktop.log 反馈。
- **窗口大小/位置想重置（或窗口跑到了屏幕外）** — 关掉本程序，删掉 `%APPDATA%\com.dsh.desktop\.window-state.json`，下次启动即回到 1376×774 居中。正常拔插显示器不需要这么做：恢复时插件只会套用「与当前某个显示器相交」的坐标。见「窗口布局记忆」。
- **更新失败** — 查看日志里 npm 的完整输出；多为网络问题或全局目录权限不足（本程序从不请求管理员权限）。若命令执行成功但 DSH 行为异常，通常是配置被**另一个版本**写过：先用安装前备份的 DSH 家目录还原，再重试。
- **WebView2 缺失** — NSIS/MSI 安装包会引导安装 WebView2 运行时。

## FAQ

**内置 Node.js 或 DSH 吗？**
否。既不内置也不嵌入，更不部署便携运行时；程序只使用你自己安装的官方版本（必要时引导你在线安装官方包）。

**配置存在哪里？**
`%APPDATA%\com.dsh.desktop\config.json` —— 当前用户目录，无需管理员权限，绝不在 Program Files。

**`latest` 和 `next` 有什么区别？我该装哪个？**
它们是 npm 的 dist-tag，不是具体版本号。`latest` 是**稳定版**（直接 `npm install -g @deepseek-ai/dsh` 装到的就是它）；`next` 是**下一版的 beta**——版本号比 latest 更新，供提前试用，可能带不兼容改动。程序用一条 `npm view <包名> dist-tags` 同时读到两个值，只要两者不同就把 `next` 视为「最新可用版本」——所以你装的若不是 `next`，状态栏就会提示有更新。弹窗里两个频道随时都能选，不受当前已装版本限制：想试新版选 `next`，想退回旧稳定版选 `latest`；两个方向都建议先备份 `%USERPROFILE%\.dsh`。见「更新 DSH」。

**用什么端口？**
默认 3080，可在首选项页修改（1~65535，带校验）。见「默认端口」。

**会管理不是它启动的 DSH 进程吗？**
不会。只按 PID + Job Object 结束自己启动的进程树；外部服务只能「连接查看」，退出时不受影响。

**关闭窗口等于退出吗？**
默认不是——隐藏到托盘。可在首选项把关闭按钮改为「退出程序」。

**为什么开机自启要等 12 秒？**
刚登录时磁盘 IO 高峰、Node/网络未必就绪，延迟可避免大多数超时失败；等待期间点「停止」可取消。

**以前能用，现在 DSH 启动不起来了——会是 Node.js 版本的问题吗？**
有可能：如果你的 Node.js 低于 22.19.0（例如 21.x）。本程序现在会直接拒绝这类启动，并告诉你检测到的版本与要求的版本，而不是只显示 DSH 那段看不懂的退出信息；按提示到 <https://nodejs.org> 安装当前 LTS（官方安装包覆盖原目录，PATH 不变），装完重启本程序即可。详见「Node.js 版本检查」。

**工具栏不见了 / 鼠标移到窗口最顶部才出来？**
这是「自动隐藏工具栏」模式（⚙ 首选项里可关闭）。它默认收起在窗口之上，鼠标进入窗口顶部 8px 的触发条时滑出，离开工具栏半秒后收回；`Ctrl+Shift+H` 可快速切回固定显示。注意两点：自动隐藏在 DSH 页面**就绪之后**才生效（DSH 还没跑起来时工具栏一直显示）；快捷键只在本启动器页面持有焦点时有效，焦点落在内嵌 DSH 页面里时请把鼠标移到窗口最顶部。见「工具栏显示模式」。

**为什么安全模式下工具栏不能自动隐藏？**
「退出安全模式」按钮与琥珀色徽标就长在工具栏上，收起它等于把人困在安全模式里，所以安全模式**强制固定显示**，首选项里的开关在这期间也会被禁用。见「工具栏显示模式」。
